# robot_navigation — автономная уличная навигация по GNSS

Пакет добавляет роботу возможность самостоятельно проезжать маршрут из
нескольких точек, заданных координатами GPS, объезжая препятствия по лидару.

Стек собран по официальному руководству Nav2
[«Navigating Using GPS Localization»](https://docs.nav2.org/tutorials/docs/navigation2_with_gps.html)
и его эталонному пакету `nav2_gps_waypoint_follower_demo`. Ничего
самодельного в критичных местах нет: курс считает `imu_filter_madgwick`,
положение — `robot_localization`, маршрут ведёт `nav2`.

## 1. Как это устроено

```
        ┌──────────── СЛОЙ ЖЕЛЕЗА (project_start/start.launch.py) ────────────┐
        │                                                                     │
 пульт ELRS ──> /cmd_vel/manual, /control_mode                                │
 GNSS       ──> /gps/fix                                                      │
 MPU6050    ──> /imu/data_raw                                                 │
 магнитометр──> /imu/mag_raw                                                  │
 энкодеры   ──> /joint_states ──> robot_odom ──> /odom                        │
 лидар      ──> /scan ──> relay ──> /scan_reliable                            │
        └─────────────────────────────────────────────────────────────────────┘
                                     │
        ┌──────────── ЛОКАЛИЗАЦИЯ (localization.launch.py) ───────────────────┐
        │                                                                     │
 /imu/mag_raw ─> mag_declination_node ─> /imu/mag   (снято склонение)         │
 /imu/data_raw + /imu/mag ─> imu_filter_madgwick ─> /imu/data (курс ENU)      │
                                                                              │
 /odom + /imu/data            ─> ekf_filter_node_odom ─> TF odom→base_link    │
                                                         /odometry/local      │
 /odom + /imu/data + /odometry/gps ─> ekf_filter_node_map ─> TF map→odom      │
                                                         /odometry/global     │
 /gps/fix + /odometry/global  ─> navsat_transform ─> /odometry/gps            │
                                                     сервис /fromLL           │
        └─────────────────────────────────────────────────────────────────────┘
                                     │
        ┌──────────── НАВИГАЦИЯ (navigation.launch.py) ───────────────────────┐
        │                                                                     │
 planner_server (NavFn) + controller_server (Regulated Pure Pursuit)          │
 costmap'ы по /scan_reliable, behavior_server (восстановление)                │

        └─────────────────────────────────────────────────────────────────────┘
                                     │

                                     │
 velocity_smoother ─> /cmd_vel/auto ─> cmd_switcher ─> /cmd_vel ─> моторы
```

### Три вещи, которые важно понять

**Почему два EKF, а не один.** Локальный фильтр (`odom → base_link`) даёт
гладкую и непрерывную оценку — по ней контроллер ведёт робота, и она не
дёргается. Глобальный (`map → odom`) привязывает робота к местности по GPS и
может скачком сдвинуться на пару метров при обновлении фикса. Разделение —
требование архитектуры Nav2: скачок происходит в трансформе `map → odom`
и не рвёт траекторию под колёсами.

**Почему магнитное склонение снимается до фильтра.** Магнитометр смотрит на
магнитный полюс, GPS работает от географического. Разница в средней полосе —
11–13°. У `navsat_transform` есть параметр `magnetic_declination_radians`, но
он влияет только на разовую привязку `map ↔ UTM`; сам курс в EKF остался бы
магнитным, и фильтр вечно боролся бы сам с собой (позиция в истинном ENU,
курс в магнитном). Поэтому `mag_declination_node` доворачивает вектор поля
**до** фильтра ориентации, и весь стек работает в одной системе отсчёта.

**Почему Nav2 не подключён к `/cmd_vel` напрямую.** Выход идёт в
`/cmd_vel/auto`, а `cmd_switcher` отдаёт приоритет пульту. Оператор в любой
момент перехватывает управление, просто двинув стик. Прямое подключение
убило бы эту страховку.

## 2. Установка зависимостей

```bash
sudo apt update
sudo apt install -y \
  ros-jazzy-robot-localization \
  ros-jazzy-imu-filter-madgwick \
  ros-jazzy-nmea-navsat-driver \
  ros-jazzy-navigation2 \
  ros-jazzy-nav2-bringup \
  ros-jazzy-nav2-regulated-pure-pursuit-controller \
  ros-jazzy-nav2-simple-commander
```

Настройка сети DDS (**обязательно, один раз**):

```bash
cd ~/ros2_ws
./setup_dds.sh
source ~/.bashrc
```

Полный стек поднимает больше двадцати процессов, а CycloneDDS по
умолчанию рассчитан на меньшее число. Без этого шага при запуске Nav2
половина узлов упадёт с `Failed to find a free participant index`.
Подробности — в разделе «Диагностика».

Сборка:

```bash
cd ~/ros2_ws
./rebuild.sh
source install/setup.bash
```

`rebuild.sh` удаляет прошлые результаты сборки и собирает всё заново одним
режимом. Это важно: смешивание `colcon build` и `colcon build
--symlink-install` ломает метаданные Python-пакетов, причём сборка при этом
проходит успешно, а падает уже запуск (см. раздел «Диагностика»).

Если предпочитаете собирать вручную, держитесь одного режима и не
чередуйте их:

```bash
colcon build            # обычный режим, надёжнее всего
```

## 3. Ввод в эксплуатацию

Порядок обязателен. Каждый шаг проверяется отдельно — так вы поймаете
проблему в гараже, а не в поле.

### Шаг 1. Калибровка магнитометра (обязательно)

Это самый частый источник неудач. Некалиброванный магнитометр врёт на
десятки градусов, и никакая настройка Nav2 это не исправит.

Ключевое, что нужно понимать: **ошибка некалиброванного магнитометра
непостоянна**. Она меняется при повороте робота — может быть +5° на север
и −150° на юг. Поэтому её нельзя измерить один раз и вычесть; нужна именно
калибровка вращением.

Запустите слой железа (питание робота включено целиком — калибруется робот
в сборе, а не датчик отдельно):

```bash
ros2 launch project_start start.launch.py
```

В другом терминале:

```bash
ros2 run robot_navigation mag_calibrator
```

Медленно вращайте робота вокруг вертикальной оси — 2–3 полных оборота за
минуту, можно прямо гусеницами с пульта. Наклонять не нужно. Утилита
показывает полоской, какая часть круга уже пройдена, и в конце печатает
готовые значения.

> Проводите калибровку на открытом месте, **подальше от металла**: не в
> гараже, не у машины, не на железном столе и не над арматурой в бетоне.

Скопируйте напечатанные значения в `config/mag_calibration.yaml`
и перезапустите робота.

#### Если утилита ругается на большое смещение нуля

Смотрите на строку `Смещение нуля: ... (Nx от поля)`. Горизонтальная
составляющая поля Земли в средней полосе — около 15–17 мкТл, и смещение
желательно иметь **меньше** этой величины.

| Отношение | Что это значит |
|---|---|
| < 1× | хорошо, можно работать |
| 1–3× | терпимо, курс поедет |
| > 3× | надо переносить плату физически |

Почему большое смещение опасно, хотя формально вычитается: поле робота
не постоянно. Когда в повороте растёт ток моторов, оно меняется. При
смещении 94 мкТл изменение всего на 5% даёт 4.7 мкТл — это 30% от поля
Земли и скачок курса до 18°. Робот будет «плыть» именно в поворотах,
то есть в самый неподходящий момент.

**Лечится только переносом датчика.** Магнитное поле убывает
пропорционально кубу расстояния, поэтому даже 20 лишних сантиметров дают
огромный выигрыш. Поднимите плату магнитометра на мачту над корпусом,
на 30 см и выше, подальше от моторов, аккумулятора и силовых проводов.

После переноса **обязательно** поправьте координаты в URDF
(`tracked_robot_description/urdf/tracked_robot.urdf.xacro`, свойство
`mag_xyz`) и прогоните калибровку заново.

### Шаг 2. Угол монтажа платы и магнитное склонение

**Угол монтажа.** Плата магнитометра почти никогда не смотрит ровно туда же,
куда нос робота. Поставьте робота на ровное место, определите реальный азимут
его носа компасом телефона (телефон держите горизонтально, в 20–30 см от
металла робота) и запустите:

```bash
ros2 run robot_navigation heading_check \
    --ros-args -p true_azimuth_deg:=210
```

Утилита напечатает готовое значение `mounting_yaw_deg` для
`config/mag_calibration.yaml`.

**Обязательно перепроверьте.** Перезапустите робота, разверните его на 90°
и повторите `heading_check` с новым азимутом. Если курс сошёлся и во второй
раз — калибровка удалась. Если во второй раз ошибка снова большая, значит
шаг 1 выполнен плохо: вернитесь к `mag_calibrator`.

**Магнитное склонение.** Откройте
[калькулятор NOAA](https://www.ngdc.noaa.gov/geomag/calculators/magcalc.shtml),
введите координаты места испытаний, возьмите поле **Declination**.
Восточное склонение — положительное число. Оно передаётся аргументом запуска
`declination_deg`, а не через файл: это свойство местности, а не робота.

### Шаг 3. Проверка локализации (без движения)

```bash
ros2 launch robot_navigation bringup.launch.py \
    declination_deg:=11.9 \
    use_navigation:=false \
    use_commander:=false
```

Вынесите робота на открытое место, дождитесь фикса и проверьте:

```bash
ros2 run robot_navigation nav_preflight_check
```

Утилита за 15 секунд напечатает чеклист: частоты всех топиков, наличие
фикса и его точность, собранность TF-дерева, работу `navsat_transform`.
Отдельно она покажет **азимут по компасу** — сверьте его с компасом в
телефоне. Расхождение больше 15° означает, что калибровка или склонение
заданы неверно, и дальше идти нельзя.

### Шаг 4. Проверка курса в движении

Поездите роботом с пульта вперёд-назад и по кругу, наблюдая в RViz
(`Fixed Frame: map`) за фреймом `base_link`. Стрелка робота должна ехать в ту
же сторону, куда он реально едет. Если робот едет вперёд, а маркер уходит
вбок или назад — курс всё ещё неверен, возвращайтесь к шагу 1.

### Шаг 5. Запуск Nav2 и пробная поездка

Первый запуск полного стека — уже с навигацией:

```bash
ros2 launch robot_navigation bringup.launch.py declination_deg:=11.9
```

Nav2 поднимается на 15-й секунде. Убедитесь, что все узлы стали активны:

```bash
ros2 lifecycle get /bt_navigator      # ожидается: active [3]
ros2 run robot_navigation nav_preflight_check
```

Теперь проверьте связку «Nav2 → мультиплексор → моторы». **Сначала
поставьте робота на подставку**, чтобы гусеницы не касались земли:

```bash
ros2 run robot_navigation send_test_goal
```

Утилита возьмёт текущее положение робота из TF, посчитает точку в трёх
метрах прямо по курсу, покажет её и спросит подтверждение. Гусеницы
должны закрутиться **вперёд**. Если крутятся назад или в разные стороны —
проблема в `invert_left` / `invert_right` / `invert_angular` в настройках
`kolesa_control`, и до выезда её надо устранить.

Затем то же самое на земле, на открытой площадке, с пультом в руках:

```bash
ros2 run robot_navigation send_test_goal --ros-args -p distance:=5.0
```

Робот должен проехать примерно 5 метров вперёд и остановиться.
Полезно повторить с поворотом, чтобы проверить работу курса:

```bash
ros2 run robot_navigation send_test_goal --ros-args -p bearing_deg:=90.0
```

Робот обязан развернуться **влево** и проехать. Поехал вправо — курс
инвертирован, возвращайтесь к `heading_check`.

> Этот шаг стоит того, чтобы его не пропускать. Он отделяет ошибки
> навигации от ошибок привода: если робот не едет по маршруту, вы будете
> точно знать, что моторы и Nav2 здесь ни при чём.

### Шаг 6. Запись маршрута

```bash
ros2 run robot_navigation gps_waypoint_logger \
    --ros-args -p output_file:=/home/pi/route.yaml
```

Катайте робота пультом, в каждой нужной точке останавливайтесь и вызывайте:

```bash
ros2 service call /gps_waypoint_logger/log_waypoint std_srvs/srv/Trigger
```

Ошиблись — `ros2 service call /gps_waypoint_logger/undo_waypoint std_srvs/srv/Trigger`.

> Запись собственным приёмником робота точнее, чем координаты с онлайн-карты:
> систематическая ошибка приёмника взаимно сокращается на записи и на
> проезде. Снимки в картографических сервисах смещены относительно
> реальности на единицы метров.

### Шаг 7. Первый автономный заезд

```bash
ros2 launch robot_navigation bringup.launch.py \
    declination_deg:=11.9 \
    waypoints_file:=/home/pi/route.yaml
```

Робот **не поедет сам**. Держите палец на пульте и запустите маршрут:

```bash
ros2 service call /gps_waypoint_commander/start_route std_srvs/srv/Trigger
```

или переведите тумблер режимов на пульте в положение **AUTO**.

Немедленная остановка — двинуть любой стик пульта (у ручного управления
приоритет выше) либо:

```bash
ros2 service call /gps_waypoint_commander/cancel_route std_srvs/srv/Trigger
```

**Первый заезд проводите на пустой площадке**, а не на улице с людьми.

Начните с коротышки: две точки метрах в десяти друг от друга. Убедитесь,
что робот доезжает до первой, паузит и уходит ко второй. Только после
этого давайте настоящий маршрут.

За чем следить на первом заезде:

| Симптом | Куда смотреть |
|---|---|
| Уходит вбок от прямой между точками | Магнитное склонение или калибровка |
| Виляет, не может доехать до точки | `xy_goal_tolerance` меньше точности GNSS |
| Уплывает курс именно в поворотах | Магнитометр ловит поле от моторов |
| Останавливается и крутится на месте | Планировщик не видит пути, смотрите костмап |
| Дёргается, движение рывками | Снизьте `controller_frequency` — не хватает CPU |

## 4. Настройка под свой робот

| Что менять | Где | Зачем |
|---|---|---|
| `robot_radius: 0.45` | `nav2_params.yaml`, оба костмапа | Габарит вашего шасси. Занижение → робот цепляет препятствия |
| `desired_linear_vel: 0.6` | `nav2_params.yaml`, `FollowPath` | Крейсерская скорость, м/с |
| `xy_goal_tolerance: 1.5` | `nav2_params.yaml`, `general_goal_checker` | Допуск прибытия. Для RTK-приёмника можно 0.3 |
| `width/height: 120` | `nav2_params.yaml`, `global_costmap` | Окно планировщика. Соседние точки должны быть ближе ~50 м (робот в центре, до края ~60 м) |
| `lookahead_dist: 1.0` | `nav2_params.yaml`, `FollowPath` | Больше — плавнее, меньше — точнее по траектории |
| `declination_deg` | аргумент launch | Магнитное склонение вашей местности |
| `gain: 0.1` | `imu_filter.yaml` | Уменьшите до 0.05, если курс дрожит от вибрации гусениц |

## 5. Диагностика

**Робот кружит вокруг точки и не может доехать.**
Допуск прибытия меньше точности GNSS. Увеличьте `xy_goal_tolerance`.

**Робот систематически уходит вбок от прямой между точками.**
Не учтено или неверно задано магнитное склонение (`declination_deg`).

**Робот едет в противоположную сторону.**
Перепутаны оси магнитометра. Проверьте `mag_yaw_offset_deg` и `mag_z_invert`
в `compass_control`, а также `world_frame: "enu"` в `imu_filter.yaml`.

**Nav2 отклоняет маршрут («Nav2 ОТКЛОНИЛ маршрут»).**
Недоступен сервис `/fromLL` — не поднялся `navsat_transform` или он ещё не
получил GPS-фикс. Проверьте: `ros2 service list | grep fromLL`.

**Маршрут прерван, в логе командира код отказа Nav2.**
`gps_waypoint_commander` расшифровывает коды из `nav2_msgs`. Частые:

| Код | Имя | Что делать |
|---|---|---|
| 204 | `GOAL_OUTSIDE_MAP` | Следующая точка за краем скользящего костмапа. Поставьте промежуточную или подъедьте ближе |
| 208 | `NO_VALID_PATH` | Нет пути: препятствие или цель за окном. Смотрите костмап в RViz |
| 105 | `FAILED_TO_MAKE_PROGRESS` | Робот застрял (трава, яма, progress_checker) |
| 102 / 202 | `TF_ERROR` | Нет трансформа `map→odom→base_link`. Проверьте оба EKF |

**Маркер робота прыгает между двумя позициями в RViz.**
Трансформ `odom → base_link` публикуют двое. Убедитесь, что `publish_tf`
выключен и у `robot_odom`, и у `kolesa_control`.

**Костмап зарастает призрачными препятствиями.**
Уберите `inf_is_valid: true` из источника `scan` — на улице лучи,
не встретившие препятствий, возвращают бесконечность и должны очищать карту.

**При запуске: `SubstitutionFailure: launch configuration 'lidar_delay' does not exist`**
Исправлено. Если ошибка всё же появилась — вы работаете на старой версии
кода, обновитесь и пересоберите. Суть ошибки: `TimerAction` вычисляет свой
`period` асинхронно, уже после того как область видимости аргументов закрыта,
поэтому подстановку в `period` класть нельзя — только готовое число.
Внешне сбой почти незаметен: остальные узлы стартуют нормально, но **лидар
не поднимается**, и Nav2 остаётся без данных о препятствиях. Проверить, что
лидар жив: `ros2 topic hz /scan`.

**Лидар не открывается: `cannot bind to the specified serial port /dev/lidar`**
Не настроено udev-правило. Начиная с текущей версии `start.launch.py` сам
подставляет `/dev/ttyUSB0`, если `/dev/lidar` отсутствует, — при запуске
он печатает, какой порт выбран. Чтобы закрепить имена намертво, создайте
`/etc/udev/rules.d/99-robot-usb.rules`:

```
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="lidar"
SUBSYSTEM=="tty", ATTRS{idVendor}=="067b", ATTRS{idProduct}=="2303", SYMLINK+="gps"
```

затем `sudo udevadm control --reload-rules && sudo udevadm trigger`.
Посмотреть свои VID:PID можно командой `lsusb`.

**При сборке `ydlidar_ros2_driver` выводит warning про unused parameter**
Это не ошибка, а предупреждения компилятора в коде производителя лидара.
Сборка при этом успешна. Ориентируйтесь на итоговую строку
`Summary: N packages finished` — если рядом нет слова `failed`, всё в порядке.

**Узел падает: `PackageNotFoundError: No package metadata was found for ...`**
Смешаны два режима сборки. `colcon build` копирует файлы, а
`colcon build --symlink-install` ставит ссылки; вперемешку они оставляют
в `install/` исполняемый файл от одного режима и метаданные Python от
другого. Коварство в том, что **сборка проходит успешно и молча**, а
падает только запуск, причём не у всех пакетов сразу. Лечится чистой
пересборкой:

```bash
cd ~/ros2_ws
./rebuild.sh          # удалит build/ install/ log/ и соберёт заново
source install/setup.bash
```

Скрипт заодно вычищает `*.egg-info` из `src/` — эти файлы остаются после
режима ссылок, переживают удаление `install/` и воспроизводят поломку
заново. Если проблема повторится, соберите обычным режимом (`./rebuild.sh`
без аргументов) — он надёжнее, хотя и требует пересборки после каждой
правки Python-файлов.

**Молчит `/imu/data_raw`, а значит и `/imu/data` (курса нет).**
Датчик MPU6050 не отвечает по I2C. Остановите стек и запустите проверку
железа — она обращается к шине напрямую и не зависит от ROS-узлов:

```bash
ros2 run robot_navigation i2c_check
```

Утилита покажет все устройства на шине, опознает известные, а для MPU6050
проверит `WHO_AM_I`, диапазон акселерометра, измерит гравитацию и
смещение нуля гироскопа.

Как читать результат:

| Что видно | Причина |
|---|---|
| Шина не открывается | I2C выключен в системе или нет прав |
| На шине пусто | Не подключены SDA/SCL, нет питания, нет подтяжки |
| Есть `0x0D`, нет `0x68` и `0x69` | Шина жива, неисправен именно модуль MPU6050 |
| Есть `0x69` вместо `0x68` | Нога AD0 подтянута к питанию — драйвер найдёт сам |
| `Errno 5` при живой шине | Плохой контакт или сгоревший датчик |

Различайте две ошибки — они означают разное:

* **`[Errno 5] Input/output error`** — устройство не подтверждает свой
  адрес. Его либо нет на шине, либо оно обесточено.
* **`[Errno 121] Remote I/O error`** — адрес подтверждается, но регистр
  прочитать не удаётся. Чип **живой и на шине**, рвётся сама транзакция.

Во втором случае причины в порядке вероятности:

**1. Стек робота не остановлен.** Узел `mpu6050_control` раз в 5 секунд
выполняет полный сброс датчика, и во время сброса (около 150 мс) чип не
отвечает никому. Проверка, попавшая в это окно, объявит исправный датчик
неисправным. Утилита `i2c_check` сама обнаруживает такие процессы и
отказывается работать — остановите `launch` и повторите.

**2. Частота шины.** Чем больше устройств, тем выше ёмкость линий и тем
хуже фронты сигналов.

Сначала посмотрите, как шина включена в `/boot/firmware/config.txt`.
Возможны два варианта, и команда для них разная:

```
dtparam=i2c_arm=on            ->  добавить ,i2c_arm_baudrate=50000
dtoverlay=i2c1                ->  добавить ,baudrate=50000
```

По умолчанию оба варианта уже дают 100 кГц, поэтому «снизить до 100 кГц»
чаще всего нечего — снижать надо до 50 кГц:

```
dtoverlay=i2c1,baudrate=50000
```

Затем `sudo reboot`. Не указывайте оба способа включения сразу: если в
файле уже есть `dtoverlay=i2c1`, строку `dtparam=i2c_arm=on` добавлять не
нужно.

**3. Длинные провода к датчику.** Самая частая причина, если вы недавно
что-то переносили. Подробности — в следующем разделе.

Начиная с текущей версии драйвер и утилита читают регистры **с повторами**
(до 5–6 попыток), поэтому одиночные сбои шины больше не приводят к отказу
и не мешают работе.

**Про UART и I2C на одних выводах.** Шина I2C-1 занимает GPIO 2 и 3.
Оверлеи `uart2`…`uart5` перечислены в справке как использующие GPIO 0–3,
4–7, 8–11 и 12–15, из-за чего кажется, будто `uart2` отбирает выводы у
I2C. На деле вторая пара выводов в каждой группе — это CTS/RTS, и они
включаются только параметром `ctsrts`, который **по умолчанию выключен**.
То есть `dtoverlay=uart2` занимает лишь GPIO 0 и 1, а SDA1/SCL1 остаются
свободны. Убедиться в этом можно командой:

```bash
pinctrl get 2,3      # на старых системах: raspi-gpio get 2,3
```

В строках должно быть `SDA1` и `SCL1`. Утилита `i2c_check` выполняет эту
проверку автоматически.

Раньше этот узел при любой ошибке инициализации завершался навсегда, и
весь стек продолжал работать **без датчика курса**, внешне выглядя
исправным. Теперь он остаётся жив, переподключается и переживает
кратковременные сбои шины уже на ходу.

### Длинные провода I2C и вынос магнитометра

Магнитометр полезно унести подальше от моторов и аккумулятора — это
резко уменьшает смещение нуля. Но у выноса есть обратная сторона:
**длинный провод портит шину целиком**, а не только себя.

Шина I2C — это две линии с подтяжкой к питанию. Каждый датчик и каждый
сантиметр провода добавляют ёмкость, а фронты сигналов формируются
зарядом этой ёмкости через резистор подтяжки. Стандарт I2C ограничивает
суммарную ёмкость линии величиной 400 пФ. Обычный провод-дюпон даёт
80–120 пФ на метр, то есть один метр съедает больше четверти всего
запаса.

Отсюда неочевидное следствие: **отвалиться может датчик на КОРОТКОМ
проводе**. Ёмкость общая, замедленные фронты видят все участники, а
первым перестанет отвечать тот, у кого меньше запас по порогам.

Измерьте качество шины объективно:

```bash
ros2 run robot_navigation i2c_check
```

В конце будет раздел «Стресс-тест шины» с долей сбоев по каждому
устройству. Ориентир: **0% — норма**, до 1% — терпимо за счёт повторов
в драйвере, больше 1% — датчики будут пропадать на ходу.

Дальше действуйте по порядку, **прогоняя стресс-тест после каждого шага**
и сравнивая проценты.

**Шаг 1. Снизить частоту шины.** Самое простое и обычно достаточное.
В `/boot/firmware/config.txt` найдите строку включения I2C и добавьте
частоту — синтаксис зависит от того, как шина включена:

```
dtoverlay=i2c1                ->  dtoverlay=i2c1,baudrate=50000
dtparam=i2c_arm=on            ->  dtparam=i2c_arm=on,i2c_arm_baudrate=50000
```

Затем `sudo reboot`. Если 50 кГц не хватило, попробуйте 10000. Датчикам
этого достаточно: магнитометр опрашивается 25 раз в секунду, IMU — 50,
данных там единицы байт.

**Шаг 2. Свить провода.** Скрутите SDA с отдельным проводом земли и SCL
с ещё одним проводом земли. Витая пара резко снижает наводки от силовых
проводов моторов. Землю тянуть обязательно рядом с сигналом, а не общим
проводом через всю раму.

**Шаг 3. Отдельная шина для дальнего датчика.** Радикальное решение:
магнитометр на своей шине, остальные датчики на своей — тогда длинный
провод больше никому не мешает. Raspberry Pi умеет создавать
программную шину на любых свободных выводах. В `config.txt`:

```
dtoverlay=i2c-gpio,bus=3,i2c_gpio_sda=23,i2c_gpio_scl=24
```

Появится `/dev/i2c-3`. Подключите к GPIO 23 и 24 магнитометр, добавьте
подтяжку 4.7 кОм к 3.3 В на каждую линию (у программной шины своих
подтяжек нет) и запускайте с указанием номера шины:

```bash
ros2 launch robot_navigation bringup.launch.py mag_i2c_bus:=3
```

**После переноса магнитометра обязательно:**

1. Прогоните калибровку заново — смещение нуля изменилось, и оно должно
   стать заметно меньше прежнего:
   `ros2 run robot_navigation mag_calibrator`
2. Заново определите угол монтажа: `heading_check`.
3. Поправьте `mag_xyz` в `tracked_robot_description/urdf/tracked_robot.urdf.xacro`.
   На курс положение магнитометра не влияет (важна только ориентация его
   осей), но дерево TF должно соответствовать реальности.

**Массово падают узлы: `Failed to find a free participant index for domain 0`**

Это не ошибка кода. Каждый процесс ROS 2 — отдельный участник сети DDS.
Когда multicast недоступен (Wi-Fi, VPN, loopback), CycloneDDS раздаёт
участникам номера из ограниченного диапазона. Полный стек робота —
около 25 процессов:

| Слой | Процессов |
|---|---|
| Железо | 10 |
| Локализация | 5 |
| Nav2 | 8 |
| Командир маршрута | 1 |
| Сам `ros2 launch` | 1 |

Пока Nav2 не запускался, укладывались в лимит. С ним — перестали.

Коварство в том, что падает **не «виноватый» узел, а тот, кому не
хватило места**, то есть случайный. В логе это выглядит как массовое
падение половины стека без внятной причины, причём каждый раз разного.

Лечится один раз:

```bash
cd ~/ros2_ws
./setup_dds.sh
source ~/.bashrc
echo $CYCLONEDDS_URI      # проверка: путь должен вывестись
```

Переменная обязана быть установлена **до** запуска `ros2 launch`: процесс
самого launch тоже создаёт участника.

Если ошибка осталась — почти наверняка живы процессы от прошлых запусков,
и они продолжают занимать места:

```bash
pgrep -a -f 'ros2 launch'     # посмотреть
pkill -f 'ros2 launch'        # закрыть вместе с деревом процессов
```

**Nav2 «не тянет» на Raspberry Pi 4.**
Глобальный костмап уже 120×120 м при разрешении 0.15 м. Если всё равно
не хватает CPU — снизьте `controller_frequency` до 10 Гц, `update_frequency`
локального костмапа до 3 Гц и разрешение глобального до `0.2`.

Полезные команды:

```bash
ros2 run tf2_tools view_frames                # схема TF-дерева в PDF
ros2 topic hz /gps/fix /imu/data /odom        # живы ли датчики
ros2 topic echo /gps/filtered                 # отфильтрованная позиция в WGS84
ros2 lifecycle get /waypoint_follower         # поднялся ли Nav2
```
